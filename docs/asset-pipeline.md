# Asset pipeline — ISIN add / resolve / repoint

> Split out of `CLAUDE.md` (2026-08-17) to keep the always-loaded file small. Content is verbatim; `CLAUDE.md` carries a one-line index entry pointing here.

- **Add one row by ISIN** (`/asset-pipeline` → the ISIN box; `POST /api/asset-pipeline/store`) — resolves synchronously (OpenFIGI-anchored) and stores the price series, so the row lands complete rather than queued. **⚠ It 409s on an ISIN already in the grid and refuses to touch it, and that guard is load-bearing: RE-RESOLVING IS DESTRUCTIVE.** `resolve()` ranks Yahoo's candidates by `med_adv_eur` and would pick the right listing every time — but **Yahoo answers a search with an EMPTY list under load instead of a 429**, and a candidate set missing the real listing hands the win to a thin foreign line. Measured: a re-resolve of Alphabet Class A (`US02079K3059`) repointed it from **GOOGL** (€8.79bn ADV, 5,502 bars from 2004) to **GOOA.VI — Vienna** (€76,634 ADV, 2,302 bars): a **75,000× thinner** listing, silently, with no error. Same failure mode as the NVDA-on-Stuttgart bug, different road. Re-resolving is a deliberate act with its own control (the per-row Resolve action). Pinned by `tests/test_add_isin_guard.py`. Status codes: **409** already present (nothing done) · **422** new ISIN recorded but unresolved (the row IS there, unmapped) · **429** Yahoo throttled · **502** real fault.
  **⚠ A ZERO-BAR RESOLUTION IS NOT A RESOLUTION** (`store_one`, same guard file). Ten distinct **Leonteq structured products** (CH ISINs, Guernsey branch) each resolved to the SAME symbol `GODE.DE` — `bars=None`, `price_from=None` — and each was written `status='ok'`. Yahoo has no listing for a structured product, so its search returns a name-alike, the ranker takes it (nothing better on offer), and ten unrelated instruments end up pointing at one empty series: ten confident rows, zero data, no error. `store_one` now records such an ISIN as **unmapped** and raises, rather than keeping a mapping that only looks like one.
  **⚠ AN ETF MUST BE REPOINTED BY ISIN, NEVER BY NAME** (`scripts/repoint_etf_listing.py`). `repoint_primary_listing.py` cannot do it: it detects on **ADV ÷ market cap** and filters `asset_class == 'equity'`, and **a fund has no market cap** — so it reports zero candidates over a grid full of thin ETFs. But the obvious fix (point `resolve()` at them) is *worse than the disease*: `resolve()` searches Yahoo **by name** and gates identity with `same_company()`, which strips corporate forms — right for an operating company, **dangerous for a fund**, because a fund's share classes have near-identical names and DIFFERENT ISINs. Both of these are in the grid: `IE00BNDS1P30` → V3GF.MI and `IE00BNDS1Q47` → V3GE.DE, *both* named "Vanguard ESG Global All Cap UCITS ETF". They differ by accumulating/distributing, which no name comparison survives — and an Acc class rolls dividends into the price while a Dist class pays them out, so the two **compound differently**. Swapping them isn't a venue annoyance, it's a **wrong price series**. So candidates are enumerated from **OpenFIGI's listings of the one ISIN** (`openfigi.lookup_isin` → `build_candidates`), which by construction contains only the venues *that share class* trades on — the safety is **structural, not a heuristic** (measured: `IE00BNDS1Q47` yields `V3GE.AS/.MI/.DE` and never V3GF). The name check that remains guards the *other* failure — `build_candidates` **constructs** `ticker + venue suffix`, and tickers are reused across venues, so a constructed symbol can land on an unrelated instrument. Pinned by `tests/test_etf_repoint.py`. **⚠ A `queued` FUND HAS NO ANCHOR AT ALL** (2026-07-14) — `--isin` now reaches a row of any status (a queued ETF has *never* been resolved: no symbol, no prices, invisible everywhere, and it is the row that most needs an ISIN-anchored resolve — `IE00BP3QZ825` iShares Edge MSCI World Momentum sat queued). But `_same_fund` gates against the **incumbent's Yahoo name**, and a queued row has none; its other two names are *both* vowel-crushed the way `_same_fund`'s docstring warns (OpenFIGI **and** Leonteq agree on `ISHR EDGE MSCI WRLD MOMENTUM`, against Yahoo's `iShares Edge MSCI World Momentum Factor UCITS ETF`), so anchoring on either rejects every candidate including the right one. The answer is **structural, not a looser matcher**: candidates all come from OpenFIGI's listings of the ONE ISIN and a fund's venues name themselves near-identically *to Yahoo*, so the anchor is their **CONSENSUS** (`_consensus_anchor`) — a constructed ticker that collided with an unrelated instrument is the outlier agreeing with nobody, and **a lone candidate is not a consensus** (that is an unchecked guess, refused). Measured: 6 venues validated, `IS3R.DE` €5.63m/day chosen over `IWFM.L` €1.45m/day (the LSE lists this share class **twice** — `IWMO.L` USD and `IWFM.L` GBp). Same-day fix: `fast_resolve` was the **last holdout still gating on the raw `_name_score >= _NAME_MATCH` floor** — here a false reject can't corrupt a row (ISIN-anchored) but it drops the *liquid* listing and strands the name on the thin one, i.e. the exact bug the function exists to prevent; it now uses `same_company`.
  **⚠ A CONSTRUCTED SYMBOL CANNOT REACH EVERY VENUE — AND NO GATE CAN RESCUE A CANDIDATE SET THAT NEVER CONTAINED THE ANSWER** (2026-07-14). Every candidate above is **built** as `ticker + venue suffix`, which quietly assumes OpenFIGI and Yahoo agree on the ticker. **On German venues they routinely do not**: iShares STOXX Global Select Dividend 100 (`DE000A0F5UH1`, held in **5** model portfolios) is `SDGPEX` on OpenFIGI's GR/GF/GD/GS lines and **`ISPA` on Yahoo's** — so we built the non-existent `SDGPEX.DE`, and **Xetra, the fund's most liquid line, was unreachable by construction**. The row sat `queued` (no symbol, no prices) while the only candidates on offer were Vienna (€31,824/day) and Zurich (€94,776/day); `ISPA.DE` does **€5.48m/day — 58× Zurich**. Liquidity ranking, the name gate and `_consensus_anchor` are all powerless here — they choose *among* candidates. The fix is a source, not a gate: `build_candidates(…, yahoo_isin=True)` adds **Yahoo's own resolution of the ISIN** (`_from_yahoo_isin` — one search, the ISIN as the query, no ticker guess in the middle). **⚠ IT IS A CANDIDATE SOURCE, NEVER AN ANSWER**: Yahoo resolves an ISIN to *a* listing, not the *liquid* one, and answers Alphabet's ISIN with **`1GOOGL.MI` (Milan)** and this momentum ETF with the thinner `IWFM.L` (€1.44m vs `IS3R.DE`'s €5.63m) — trusting it outright rebuilds the very bug this file exists to prevent, so it only ever ADDS to the pool and the ranker still decides (verified: `IE00BP3QZ825` keeps `IS3R.DE`). It's **off by default** — `fast_resolve` is ~1 Yahoo call/ISIN on a bulk run and doubling that is how you get throttled into the empty-list failure mode; only the deliberate per-row repointers opt in. Because it can only add, an empty/throttled search **costs the improvement, never the correctness**. One filter: Yahoo hands back a **pseudo-symbol** for some funds — the ISIN itself plus a suffix (`IE00BNDS1P30.SG`) — which is a placeholder, not a listing. Pinned by `tests/test_etf_repoint.py::TestTheConstructedSymbolCannotReachEveryVenue`.
  **Bulk-add from the AIRS portfolios**: `scripts/add_portfolio_isins.py [--dry-run] [--limit N]` — collects every ISIN across all model portfolios, diffs against `asset_execution`, and adds **only the missing ones** (never re-resolves), printing the resolved symbol + median traded value per row and flagging anything under €250k/day as a **THIN** listing to review. Measured: 248 distinct ISINs across 57 portfolios (38 have no composition), 210 already present, 38 added → 21 priced, 17 unmapped.
