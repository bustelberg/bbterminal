# Key conventions + known issues

> Split out of `CLAUDE.md` (2026-08-17) to keep the always-loaded file small. Content is verbatim; `CLAUDE.md` carries a one-line index entry pointing here.

## Key conventions

- Backend wraps blocking Supabase calls in `asyncio.to_thread()`. SSE for long ops (ingest, scanner, backtest, current portfolio), with `: keepalive\n\n` comments before long work to beat proxy timeouts.
- **Live dashboards use SSE, not polling** (2026-07-01). `routers/_sse_stream.py` turns "compute the current payload" builders into ONE push stream that re-emits a topic only when it changes (frame = `{topic,payload}` inside `data:`, since the frontend `runSSE` only parses `data:` lines): `snapshot_stream_response` (multi-topic, per-topic recompute intervals — fast while a run's active, slow idle), `status_stream_response` (single `{running}` status, closes when done), `run_detail_stream_response` (one `ingest_run` until terminal). Endpoints: `/api/schedule/stream` (the /schedule activity card's 7 topics), `/api/usage/stream` (ApiUsageBadge), `/api/ingest/runs/{id}/stream` + `/api/companies/{market-cap/refresh,openfigi/verify}/stream` (the transient job-watch UIs). Frontend: **`lib/hooks/useEventStream.ts`** (multiplexed consumer — opens on mount + tab-visible, **closes when hidden**, reconnects with backoff, sets `failed` after N fails so callers fall back to polling) and **`lib/watchRun.ts`** (`watchRun(id, onUpdate, signal)` streams one run to completion). Every migrated surface keeps its `usePollingFetch` path as an automatic fallback (enabled only when `failed`), so SSE issues degrade to polling, never breakage. `usePollingFetch` itself now also pauses while the tab is hidden. Net: an idle /schedule tab makes **zero** requests (was ~10/min).
- **⚠⚠ THE AIRS FRESHNESS BADGE MEASURES *AIRS's VALUATION DATE*, NOT OUR COPY — AND ITS REMEDY WAS FALSE** (2026-08-17). `Provenance` turns its `i` amber when `snapshotFreshness(as_of).tone === 'stale'` (≥2 trading days), and `as_of` is the day **AIRS valued the book**, not when we read it. The tooltip said *`"Refresh from AIRS" pulls the current book`*, which reads as "press this and it clears". It cannot: `_vermogen_most_recent` already walks back to the most recent *available* valuation, so a refresh returns the same date whenever AIRS has published nothing newer. Measured straight after a full "Refresh all": **31 accounts re-scanned, the newest valuation AIRS returned for ANY of them 2026-08-15, twenty still dated 2026-08-11/12 — 32 of 40 rows amber, none clearable by the action the tooltip named.** The number is true (those snapshots ARE old); the remedy was not. Fixed by pairing it with **`fetched_at`** (`airs_account_roster.reports_at`, now on the account + overview rows): `lib/snapshotAge.ts::lagOwner(asOf, fetchedAt)` returns `side: 'source'` (recent fetch, old valuation — nothing to do) or `'ours'` (old fetch — Refresh helps), and the card grows a **"Whose lag"** field. ⚠ It returns **null** rather than guessing when `fetchedAt` is absent — most `Provenance` call sites have no such fact. ⚠ **One threshold for both sides** (≥2 trading days), or the explanation eventually disagrees with the badge it explains. Pinned by `lib/lagOwner.test.ts`. ⚠⚠ **And the scan's own summary said the opposite in plain English**: `format_run_message` read *"44 already up to date"* — every count in it is about OUR COPY (what we fetched, when), while the row badge measures AIRS's valuation date, so the two were flatly contradictory and the reader was right to believe the pessimistic one. Measured on `DealmakersTopSelectie Offensief`: fetched 13:15 today, all five reports, `as_of` **2026-08-12** — complete, current *and* three trading days old, all at once. It now reads *"3 portfolios added, 28 re-read, 14 skipped (we read them within 20h) · newest AIRS valuation 2026-08-15"* — the phrase says what it means, and **the data's own date rides in the same sentence** (also appended to the job summary), so the counts cannot be read as a claim about today. ⚠ The date is omitted when the run read nothing (a skip-everything run learned no valuation date; printing the stored one states a finding it did not make), and `failed` still comes before it. Pinned by `tests/test_airs_run_message.py`. **Related trap in the same table**: `bogus_accounts` (books under `MIN_REAL_HOLDINGS`) are deliberately never re-scanned, so their `reports_ok` verdict freezes — 14 of them still record the pre-2026-08-05 report set. They escape the amber `missing_reports` badge only because `_missing_reports` filters to the *newest* `reports_at` batch; if that filter ever goes, they will all light up permanently.
- **⚠⚠ "CAGR" HAS EXACTLY ONE DEFINITION AND IT IS POINT-TO-POINT** (2026-08-17). The Long Equity growth card used to headline the **slope of a fitted exponential** (`logLinearFit`) while the Tables tab measured **endpoints**, so one book's FCF/share read 29.7% on one screen and 30.1% two tabs away — a *modelling* difference nothing on either screen named, and not a fixed offset (it is however far the endpoint years sit off the trend, so it moves per company and per metric). Both now go through `portfolios/lineCagr.ts`: `endpointCagr(points)` for the card, `lineCagr(level, years)` for the table, one arithmetic. **The fit is still computed and still drawn** — R² and the trend overlay are the fit, and that is the right split: the fit answers *how steady*, the CAGR answers *what the rate was*, so the trend line may sit slightly off the two points the number connects and that gap **IS** what R² measures. ⚠ Consequences: the card **refuses** (—) where the series is non-positive at either end instead of quietly fitting the positive years (that was already a documented mislabel — "over 9 years" against a fit over 2017-2025), and both tiles now **state their window**, because the card spans its whole drawn series while the table pins exactly 5/10 years back from `commonEndPeriod`. Pinned by `endpointCagr.test.ts`.
- **⚠⚠ `_page_metrics` MUST PAGE ON A UNIQUE SORT KEY — THE SECOND TIME THIS EXACT BUG HAS SHIPPED** (2026-08-17; the first was the FX pager). It ordered on `target_date` **alone**, and a company files ~110 metric codes on the *same* date, so at `_PAGE = 1000` **every** page boundary fell inside a tie group — and Postgres makes no promise about tied rows across separate LIMIT/OFFSET queries. Rows come back twice or never. Measured on Bustelberg Offensief's FCF/share: **ASML, Alphabet and Amazon each silently lost their 2018 figure and Berkshire its 2019** — a different arbitrary row per company, no error, no empty panel, just a blended line missing a point (0.14pp on the book's 10y CAGR). ⚠ **It was visible only as a disagreement between two screens**: the Tables tab reads the same function with `exact=True` — ONE code, ~28 rows — so it never reaches a boundary and was correct throughout. Now `.order("target_date").order("metric_code").order("source_code")` (the PK is `(company_id, metric_code, source_code, target_date)` and `company_id` is pinned by the filter). ⚠ **A stable server-side order hides it completely**, which is what a local Postgres or a small table will hand you — so `tests/_fake_supabase.py` gained **`unstable_ties=`** (rotates each tie group per query); use it to prove any pager's ORDER BY is total. Pinned by `tests/test_metric_paging_ties.py`, which also asserts the harness itself reproduces the bug.
- **⚠⚠ A METRIC KEY IS A REGISTRY LOOKUP AND AN UNKNOWN ONE IS REFUSED — NEVER DEFAULTED TO REVENUE** (2026-08-17). `routers/earnings.py::_metric_codes` was `_METRIC_CODES.get(metric, _METRIC_CODES["revenue"])`, so a key the registry doesn't carry came back as a **different, valid, plausible series** under whatever label the caller had already written. `TablesTab` asked `portfolio-revenue-matrix?metric=fcf_per_share` (the key is **`fcf_ps`** — `LongEquityTab`'s `CARDS[].benchmarkMetric` has it right, which is why the card and its drill-down agreed with each other), so its row labelled "FCF / share CAGR" was the book's **revenue** growth: Bustelberg Offensief read **+19.0%/yr** against the Long Equity card's **+28.0%** on the same book, window and modal. **Nothing errored and no cell was empty** — the only symptom was two numbers disagreeing, and the tab's own footnote offered a *credible wrong explanation* (point-to-point vs the card's trend fit), which is what let it survive. Measured, that explanation is worth **0.5pp**: the fit is 27.46% and point-to-point on the SAME line is 28.00%. **At a high R² the two cannot diverge much — R² IS how close the line is to a constant-rate exponential — so a large gap is never the fit; it means the two sides are reading different series.** `_metric_codes` now raises `ValueError` and `portfolio-revenue-matrix` validates into a **422** naming the valid keys (safe: every other caller passes a literal). ⚠ These keys are **plain string literals in `.tsx` with nothing checking them at build time**, so a rename on either side compiles, deploys and renders. Pinned by `tests/test_metric_key_typo.py`.
- **The Fundamental reads are cached in memory, in `apiFetch`** (2026-08-12, `frontend/lib/readCache.ts`). The Fundamental modal (Long Equity · Quick Valuation · Deep Valuation · Old charts) is ~14 requests per company, and everything except switching tabs inside ONE open modal re-paid all of them: reopening the same holding, opening a drill-down over a card that had just POSTed the identical body, flipping the cadence to quarterly and back, ticking a benchmark off and on. A hit is replayed as a normal `Response`, so no call site changed. Three rules: (1) ⚠ **an ALLOWLIST of paths, never "every GET"** — half this app is a live dashboard (usage, run status, price coverage) and serving those from memory would show a finished job as still running; every allowlisted path is derived from `metric_data`, which changes only by an ingest. Missing a new read endpoint costs a speed-up, adding a live one costs correctness. (2) ⚠ **any successful write drops the whole cache, and that rule lives in `apiFetch`, not at the ~15 "Fetch financials" buttons** — a cache that depends on fifteen callers remembering to invalidate it is one that will show "No revenue ingested" straight after the ingest that loaded it. The exception is a write that only STARTS a job (`PortfolioFundamentalsRefresh`, `FundamentalGridPane`): the POST succeeded minutes before the data moved, so those call `invalidateReadCache` on completion. (3) ⚠ **the read POSTs must be exempt from that rule** — `fundamental-blend-metrics/stream` and `/api/airs/basket/analysis` are POSTs, so "any write invalidates" would have the most expensive read on the page, and the Analyse modal the Fundamental one opens from, wiping the cache every time they ran. The blend can't live in the map at all (an SSE body cannot be replayed), so `blendMetrics` memoises its RESULT against the cache's generation. 10-minute TTL as a backstop for an ingest this tab cannot see; 32 MB ceiling, oldest-first (one company's `/metrics` is 12,375 rows). Pinned by `lib/readCache.test.ts`. In the modal this pairs with `OwnerEarningsModal`'s mount set (a visited tab stays mounted, keeping its parsed charts and toggles); the cache keeps the payloads, so a tab that HAS to remount still costs nothing.
- AIRS portfolio data is parsed server-side, cached client-side in localStorage (no DB).
- Company deletion cascades: removes `metric_data` + `portfolio_weight` first.
- **The GuruFocus legacy API never 404s** — `stock/{sym}/<anything>` returns HTTP 200 and a 46-point all-zero series for any unrecognised sub-path, so `stock/AAPL/news`, `splits`, `guru`, `segments`, `profile`, `valuation`, `rank`, `earnings`, `indicator_price`, `analyst_estimates` all *look* like working endpoints and are not. **Always probe against a canary sub-path.** The catalogue of what actually works lives in [`docs/gurufocus_api.md`](docs/gurufocus_api.md) + `backend/gurufocus_api.json`, regenerated by `scripts/gurufocus_catalog.py` (responses cached in gitignored `backend/.gurufocus_cache/` → a re-run costs 0 API calls; `--max-calls` caps the spend). Pinned by `tests/test_gurufocus_catalog.py`. It has **no official documentation** — `gurufocus.com/api/overview` documents a *different, newer* product our key doesn't authenticate against. Undocumented but real and load-bearing: **`isin/{ISIN}`** and **`cusip/{CUSIP}`** → `[{symbol, exchange}]` for every listing worldwide, and **`exchange_list`** → `{region: [codes]}`. **`stock/{sym}/dividend` (singular) is per-share; `dividends` (plural) is cash-flow-for-dividends in $ millions, negative** — not the same thing.
- **Never compare company names with a raw `_name_score >= _NAME_MATCH` floor** — use `asset_pipeline.resolve.same_company()`, which strips corporate forms first. `rapidfuzz.token_set_ratio` scores `"NVIDIA Corporation"` vs OpenFIGI's `"NVIDIA CORP"` at **75.9** (floor 80), `"Intel Corporation"`/`"INTEL CORP"` at 74.1, `"Eli Lilly and Company"`/`"LILLY(ELI) & CO"` at 50.0. Until 2026-07-10 `resolve()`'s OpenFIGI name anchor used the raw floor, concluded the most-liquid `NVDA` was a *different company*, and swapped in `NVD.SG` — Stuttgart, EUR, €1.6M median daily traded value against Nasdaq's €28,076M. `identity_status()` always used `same_company`; the anchor was the odd one out. Pinned by `tests/test_asset_resolve_anchor.py`. To find the same class of defect elsewhere use **median daily traded value ÷ market cap** (`< 1e-5`; median is `4.6e-3`) — NOT an exchange-code map (Vienna≠Prague) and NOT "ISIN country ≠ listing country" (that flags every deliberate ADR→ordinary mapping). `scripts/repoint_primary_listing.py` does this; ~302 rows still flagged. **⚠ A MISSING MARKET CAP IS A SIGNAL, NOT A REASON TO SKIP** (2026-07-14): the ratio needs a cap, so a row without one was passed over — but **a dead listing is precisely what reports no cap**, so the rows most likely to be wrong were the ones the detector never looked at. Brown & Brown (`US1152361010`) sat on **BTW.DE** (Xetra, EUR, **€7,836/day, no cap, NOT ONE PRICE BAR**) while NYSE `BRO` does **€154m/day — 19,698×**; `--isin`, documented as "bypassing the ratio filter", still tripped over the cap the ratio is *computed from* and reported "0 candidates". Both fixed: `--isin` bypasses the cap too, and `--no-cap-max-adv 1e6` sweeps the blind spot (**221 equity rows have no cap; 112 trade under €1m/day** — Pool Corp on Milan at €1,042/day vs `POOL` at €142m, **136,740×**). **⚠⚠ BUT THAT CAP CHECK WAS ALSO, BY ACCIDENT, THE FENCE KEEPING FUNDS OUT OF A NAME-BASED RESOLVER** — funds report no cap (**all 29 ETP rows**), so removing it immediately produced `JE00BN7KB557` **WisdomTree Coffee** (an ETC on coffee futures) → **`LKNCY`, Luckin Coffee Inc**, a Chinese coffee *retailer*: `same_company("Luckin Coffee Inc", "WT COFFEE")` is **True** (token_set_ratio exactly 80.0 — the word "coffee" carries it), and nothing downstream would catch it because LKNCY is real, liquid and priced. The fence is now **explicit and structural** — an **allowlist** `_NAME_RESOLVABLE_TYPES` (Common Stock/ADR/GDR/REIT/…; unknown type ⇒ refused, and **no `openfigi_name` ⇒ refused**, since the identity gate is `if figi_name and …`, i.e. no name = *no gate*), it holds even under `--isin`, and refusals are printed, never silent. Closed-End Funds mostly *do* have a cap, so the hole predated the sweep. A fund is repointed by **`scripts/repoint_etf_listing.py`** (venues enumerated from the ISIN itself). Pinned by `tests/test_repoint_primary_listing.py`. **The lesson: the protection was incidental, therefore invisible, therefore removable without anyone noticing.**
- GuruFocus subscription covers USA + **continental** Europe + Asia (incl. Middle East) EXCEPT **India** (NSE/BOM — note GuruFocus + IBKR use `BOM`, not `BSE`, for the Bombay exchange; our DB stores `BOM`), **UK** (LSE), and **Ireland** (DUB) — GF returns "403 unsubscribed region" for those (confirmed by probing every exchange); Russia, Africa, LatAm, AU/NZ also out of scope — see `FEASIBLE_GF_EXCHANGES` in `backend/index_universe/acwi/exchange_map.py`. **US OTC Pink (`OTCPK`) IS covered** (USD) — GuruFocus prices US OTC tickers, so UK/foreign names with a US OTC line (e.g. QinetiQ → `OTCPK:QNTQF`) are fixable to a priceable listing instead of staying on their out-of-scope home exchange. Out-of-coverage listings get no price/mktcap/ISIN data and show the **UNSUBSCRIBED** badge on `/companies` (`is_gf_subscribed_exchange`).
- **Duplicate prevention**: two companies are the same security iff they share an **ISIN**. `ingest/dedupe.py::dedupe_by_isin` merges same-ISIN rows of the same company (name-root match, ignoring ADR/ADS) keeping the **Leonteq holding, else USA/EU** listing; it runs at the end of every `backfill_isin` so cross-universe dupes can't persist. The `/companies` DUPE badge is ISIN-based (NOT name-based — name-matching false-flags GOOG/GOOGL-style share classes that have *different* ISINs). A complementary **NAME DUPE** badge (`frontend/app/components/company/nameDupe.ts`) catches the gap the ISIN badge can't: same-name companies where **≥1 side has no ISIN** (e.g. a no-ISIN LongEquity stub duplicating a Leonteq holding — the Celestica TSX:CLA vs TSX:CLS case). The name key strips only trailing corporate-form suffixes (Inc/Ltd/Corp/SA/ADR/…) so "Celestica" ≡ "Celestica Inc" but "BYD Co" ≠ "BYD Electronic"; the no-ISIN condition keeps legitimate both-have-ISIN share classes from flagging. Surfaced as a header count + filter + per-row badge. **Prevention**: `ingest/dedupe.py::merge_name_dupes_keep_isin` auto-folds a no-ISIN stub into the same-name ISIN row — runs after `dedupe_by_isin` (in `backfill_isin`) and in the prune phase (`ingest/phases/prune.py`). SAFE by construction: acts only on a name bucket with **exactly one** ISIN-bearing company, and folds a stub only when `_foldable_names` holds (the stub's name is the keeper's name plus *only* trailing corporate suffixes — so `Celestica`→`Celestica Inc` and `HDFC Bank Ltd`==`HDFC Bank Ltd` fold, but `Siemens Ltd` (India) does **not** fold into `Siemens AG`, nor `Apple`→`Apple Hospitality`). The frontend badge uses the identical rule (`nameDupe.ts` `foldable`) so it shows exactly what prevention will clean up. Tests: `test_name_dupe_merge.py` (backend, incl. the Siemens guard) + `nameDupe.test.ts` (frontend).
- **Cross-ISIN dupes + manual overrides** (`company_override` table, migration `20260617002000`; `ingest/company_overrides.py`): the case NEITHER ISIN- nor name-dedup can catch — the **same issuer on two listings with DIFFERENT ISINs** (an ADR vs its home line: New Oriental NYSE:EDU `US…` vs HK `KYG…`; BP NYSE:BP `US…` vs London `GB…`). `dedupe_by_isin` misses it (different ISIN), the name passes miss it (both have ISINs / names differ). Mechanism: a `company_override` row of kind **`alias`** (`isin` secondary → `canonical_isin` keeper) — `apply_company_overrides` merges the secondary INTO the canonical, moving memberships + market cap but **dropping the secondary's prices** (different listing/currency — the keeper repopulates from its own). Kind **`exclude`** (matched by `isin`, else `(ticker,exchange)`) marks an unwanted-but-real constituent `out_of_scope_at` (e.g. GE Vernova T&D India NSE) so it stays suppressed after an index reconstruction re-creates it. The pass runs every ingest (prune phase + after `backfill_isin`), so a consolidation **sticks across reconstructions** (idempotent — no-ops once resolved). Seeded with New Oriental + BP (aliases) and GE Vernova India (exclude). Tests: `test_company_overrides.py`. ⚠ **The by-hand helpers are GONE** (removed 2026-08-03 as dead code — none had a caller): `merge_companies(loser, winner, …)`, which used to auto-record the loser→winner ISIN alias so a re-created loser self-healed, plus `record_isin_alias`, `add_exclusion` and `set_company_isin`. To consolidate two rows now, **insert the `company_override` row directly** (kind `alias` / `exclude` / `set_isin`) and let `apply_company_overrides` — which is still what every ingest runs — do the merge on the next pass. That was always the mechanism; the helpers were only a typing shortcut.
- Price/volume cutoff `1998-01-01`; no earlier data stored.
- **Company price-status markers** (`company.*_at` timestamps, all exclude the row from the `/api/data/price-coverage` freshness measure): `delisted_at` (stopped trading / acquired — also dropped from price refreshes; auto-set by the stale-price delisting sweep `ingest/delisting.py`, >15 trading days behind the global-latest close), `out_of_scope_at` (outside GuruFocus coverage), `illiquid_at` (trades rarely → stale GF prices but still listed; **manual** marker, still priced — set via the /schedule "Mark illiquid" button → `POST /api/admin/company-illiquid`). `/api/data/price-coverage` returns the freshest + most-stale **active** company (name/ticker/exchange/date) so the /schedule month-end refresh can verify prices actually moved.
- Supabase `.in_()` queries batched in chunks of `IN_CHUNK_SIZE` (=200, `deps.py`) — Cloudflare 502 guard. (Note: `ingest/prune_companies.py` still hardcodes its own `_IN_CHUNK = 50` — drift worth unifying.)
- **PostgREST runs over HTTP/1.1** (`deps.py` `_build`): postgrest-py hardcodes `http2=True` on its httpx session, but Supabase's Cloudflare gateway caps requests-per-connection and sends an HTTP/2 GOAWAY once hit — httpx surfaces that as `RemoteProtocolError: ConnectionTerminated` on the in-flight request, so a chatty per-row read sweep (e.g. the price refresh's per-company `_db_max_date`) hits a run of failures mid-batch. `_build` swaps postgrest's session for an HTTP/1.1 one (copying the base_url + auth headers it already set) — no GOAWAY-mid-stream failure mode. Best-effort (falls back to the default client if supabase-py internals move). Complementary fix: the prices phase's concurrent workers no longer each query `_db_max_date` per company × metric — `ingest/prices.py::prime_db_max_dates` precomputes both metrics' latest dates in ONE grouped COPY query per metric (`_pg.py::load_latest_metric_dates_via_copy`, per-company PostgREST fallback) into a batch cache the workers read; the phase clears it in a `finally`.
- GuruFocus raw responses cached in Storage bucket `gurufocus-raw`; paths `{EXCHANGE}_{TICKER}/indicator__price.json` and `indicator__volume.json`.
- **Momentum signal cutoff is strict `<`** (`signals.py`) — never train on the bar we trade; companies with last trade > 30 days before `as_of_date` are dropped. The panel anchors a cutoff to `searchsorted(side="left") - 1` (the last bar strictly before it), so a non-Monday `rebalance_weekday` (e.g. first-Wednesday) decides on the prior trading day's (Tuesday's) close and enters at the rebalance day's close. `rebalance_weekday` (0=Mon..6=Sun) is a per-variant sweep axis on `/backtest` (`VariantSpec.rebalance_weekday`; UI "Rebalance day" picker, Mon–Fri); the variant key gets a `w<n>` tag. Pinned by `tests/test_rebalance_weekday.py`.
- Transient Storage / `metric_data.upsert` errors retry up to 3× with backoff via `_retry_transient` (`ingest/prices.py`).
- **Held-basket return — ONE source of truth** (`momentum/portfolio_math.py`): a portfolio return is computed in exactly ONE place and every surface DISPLAYS it; nothing recomputes. The chain: each holding's `forward_return_pct` = `holding_eur_return_pct(h)` = `exit_price_eur/entry_price_eur − 1` (EUR; companies priced from metric_data, ETF overlays from benchmark_price, both EUR-converted at each date's fx_rate by the re-pricer); the snapshot's `period_return_pct` = `portfolio_eur_return_pct(holdings)` = Σ weight·forward. The writers (`compute_and_save_price_update`, `_apply_etf_overlay_to_snapshot`) call these — they don't roll their own. **Consumers READ, never recompute**: the /schedule header MTD (`_schedule_hydration._hydrate`, for an open period this month) + the Current-portfolio card (`CurrentPortfolioCard.tsx` — pure display: Total = `period_return_pct`, per-row = `forward_return_pct`, €cols = stored marks) + run-history all read `period_return_pct`, so they cannot disagree. Invariants pinned in `tests/test_portfolio_math.py`. A holding without EUR marks (an ETF in a snapshot taken before the EUR re-pricer ran) shows a blank €cell but a correct return; `scripts/backfill_snapshot_eur.py` re-bases old snapshots local→EUR in place. **When adding any "portfolio/holding return" surface, READ the stored value — do not recompute from prices/FX.**
- **Cash allocation** (2026-07-01): a per-strategy cash sleeve lives in `scheduled_strategy.config["cash_pct"]` (0..1, like `etf_overlay`). `portfolio_math.apply_cash_allocation(holdings, cash_pct)` strips any existing cash, **renormalizes the rest to sum-1** (so it's idempotent — the re-pricer reads a cash-baked rebalance snapshot), scales them by `(1-cash)`, and appends `make_cash_holding` (`company_id=0`, `is_cash`, flat 1.0 EUR marks → 0% return). Weighted into `period_return_pct` it IS the cash drag. Applied in both writers: `compute_and_save_price_update` (reads live `cash_pct`) + rebalance (`_apply_cash_to_snapshot` after the ETF overlay). Admin sets it via `PATCH /api/scheduled-strategies/{id}/cash` (admin-only — `_USER_WRITE_PREFIXES` is empty, so non-admin writes 403; users see cash read-only) which saves config + re-prices immediately (the seed snapshot is `kind='rebalance'`, so even a never-run strategy re-prices). Frontend: `CurrentPortfolioCard` renders a "Cash" row + an admin `CashControl` (0–100%). **Cash also scales all BACKTESTED stats**: `_schedule_hydration._scale_curve_returns` applies the cash-drag transform (scale each period's return by `1-cash`, recompound) to the backtest daily curve (`_load_backtest_pts`) + the fully-invested open-basket live curve (`_open_basket_live_curve`) — NOT the snapshot walk, already cash-aware — so `_extended_curve`/`_returns_from_backtest`/`build_live_curve` feed cash-adjusted since-inception / MTD / YTD / daily-returns / monthly-heatmap / equity-curve. Risk-metrics: annualized return + max-drawdown scale (recomputed via `_curve_stats`), **Sharpe/Sortino are cash-INVARIANT** (mean & vol both scale → ratio unchanged — mathematically correct, kept from the stored summary). The frontend `SourceBacktestCard` scales its own pre-cutover backtest daily curve with `scaleCumCurve` (mirrors the backend transform) so the equity line/heatmap join the server-scaled live tail continuously. Tests: `test_portfolio_math.py::TestCashAllocation` (idempotency/renormalize guard), `test_forward_curve.py` (`_scale_curve_returns`/`_curve_stats`), `seriesMath.test.ts` (`scaleCumCurve`). **In the diversifier**, cash is a first-class manual asset alongside ETFs: `SimHolding.is_cash` → `_assemble_holdings` emits a flat-0%-return `"Cash"` sleeve over the strategy's window (group `"cash"`) so the manual backtest/heatmap show the drag; the frontend `ManualPortfolioSection` always shows a "Cash" row (settable %). `schedule-as-strategy` converts that cash weight to `config.cash_pct` (excluding it from the strategy/ETF selection), so a scheduled diversified portfolio holds cash via the same sleeve.

- God-components: `Schedule.tsx`, `AcwiUniverse.tsx`, `CompanyManager.tsx`, and `UniverseScreener.tsx` were decomposed on 2026-06-04 (now thin orchestrators over `app/components/{schedule,acwi,company,universe}/` — see **Component notes**). `MomentumBacktester.tsx` (~670 lines) is the remaining one to keep shrinking: config + variants now decomposed and the current-picks UI removed; remaining bulk = saved-runs handlers + `loadBacktest`/`saveVariantsBundle`. Widen by extracting logic out of components into testable modules as you touch them (`portfolios/startWeights.ts`, `momentum/feeStats.ts`, `company/nameDupe.ts` are the pattern).
- **`fx_rate` history is thin and `load_fx_rates` hides it.** `momentum/data/fx.py::load_fx_rates` does `.reindex(daily).ffill().bfill()` — the **bfill** silently extends the earliest stored rate backwards to whatever `start_date` you ask for. `sync_fx_rates_to_db` only ever extends **forward** (reads stored max, fetches max+1), so nothing backfills earlier history. Before 2026-07-10 USD/CZK/GBP/JPY/CHF all started at `2024-03-07`. Any backtest whose window starts before a currency's stored minimum converts that whole stretch at one wrong rate. Not currently biting (scheduled strategies start 2025-05-02 and the backtest stream syncs FX forward first), but `/backtest` lets you pick an earlier start. `routers/_asset_dividends.py::_backfill_fx_history` shows the backwards pattern.
