# BBTerminal

A financial data terminal for wealth management. Analyses stocks using data from LongEquity reports and index universes (S&P 500, ACWI), enriched with price/volume data from GuruFocus. Includes a momentum portfolio backtester and a live "current picks" view.

> **Resuming?** Open follow-ups / unfinished work live in [`TODO.md`](TODO.md) (repo root). Check it at the start of a session.

## Architecture

- **Frontend**: Next.js 16 (App Router) on Vercel — `frontend/`. All components are client components (`'use client'`).
- **Backend**: FastAPI (Python, `uv`) on Railway — `backend/`.
- **Database**: Supabase (Postgres) — schema in `supabase/migrations/`, full ERD in [`docs/schema.md`](docs/schema.md).
- **Auth**: Supabase Auth (email/password).
- **Supabase**: one hosted prod project + a local Supabase for dev. Local is the working dataset; the old hosted dev project no longer exists.

## Running locally

Prereqs: Docker Desktop (local Supabase), Node + npm, Python + uv.

1. `npx supabase start` — boots all Supabase services locally (Studio `:54323`, REST `:54321`, DB `:54322`, Mailpit `:54324`). First run pulls images.
2. Create `.env.local` files (both gitignored). Run `npx supabase status` for the local keys:
   - `backend/.env.local`: `SUPABASE_URL=http://127.0.0.1:54321`, `SUPABASE_SERVICE_KEY=<secret key>`.
   - `frontend/.env.local`: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` (publishable key), `NEXT_PUBLIC_API_URL=http://localhost:8000`, `NEXT_PUBLIC_ALLOWED_EMAILS=<your email>`.
3. Run: `cd backend && uv run uvicorn main:app --reload --port 8000` and `cd frontend && npm run dev` (frontend `:3000`, backend `:8000`).

Useful: `npx supabase status` (URLs/keys), `db reset` (wipe + re-migrate + seed — **ask first, see memory**), `migration new <name>`, `db diff`, `db push` (→ prod), `stop`.

**Env precedence**: backend loads `.env` (prod defaults) then `.env.local` with `override=True`; on Railway `.env.local` is absent so only env vars apply. Frontend follows Next.js convention (`.env.local` overrides `.env`); Vercel uses dashboard env vars.

## Backend (`backend/`)

**Entry point**: `main.py` (~110 lines) — thin bootstrap: constructs `FastAPI()`, attaches CORS + the API auth-gate middleware, mounts each domain router, registers APScheduler. All endpoints live under `routers/`. Full endpoint list: `main.py` + `backend/openapi.json` (the source of truth — don't catalog endpoints here).

**Top-level modules**: `deps.py` (Supabase client factory + env loading — routers import from here, never `main`) · `scheduler.py` (in-process APScheduler ticks) · `portfolio.py` (parses AIRS Excel, YTD returns in EUR + local) · `airs_scanner.py` (Playwright AirSPMS scraper) · `fx_rates.py` (ECB/Yahoo FX → `fx_rate` table) · `common/pg.py` (the direct-Postgres `COPY` transport — `_run_copy`/`copy_path_enabled`; lives in `common/` because `timeseries` needs it and `timeseries → momentum` would be a cycle; `momentum/data/_pg.py` re-exports it).

**`timeseries/`** — ONE interface for every per-entity time series (2026-07-10). `load_series(entity_ids, series, start, end)` → `entity_id, date, <alias>`; `to_panel(df, value)` → wide `date × entity` (a `factorize` + numpy scatter, **6× faster** than `pivot_table`, identical output). `registry.py` names each series by **vendor + entity domain** — `gf.close` / `gf.volume` (`company_id`, `metric_data`, GuruFocus) vs `yf.close` / `yf.volume` (`analysis_id`, `asset_price`, Yahoo). `resolve()` **refuses to mix the two domains** (`company_id` and `analysis_id` are disjoint id spaces; only 2,065 of 16,150 `asset_execution` rows bridge by ISIN) and refuses to fuse two EAV rows of `metric_data` into one query. The vendor is part of the series key on purpose: `/schedule` is priced off GuruFocus, and `yf.close` is a different number. **Transport, not format, is where the speed is** — the same query is ~1,080 ms through PostgREST's 1,000-row pagination and ~89 ms through one `COPY`.

**`signal_engine/`** — ONE declaration of all 19 signals (2026-07-10). `registry.py`: `key` is cadence-namespaced (`daily.mom_12_1`, `me.mom_12_1`), `name` is the legacy public string that saved `scheduled_strategy.config["signal_weights"]` and the `/signal-lab` API are keyed by — **names are not unique across cadences, and that is the point**. `daily.py` owns the `daily_asof` math + the as-of discipline (`evaluate_panel`: strict `<` cutoff, `MIN_BARS=20`, `MAX_STALENESS_DAYS=30`); `momentum/signals.py` is now a 174-line universe-join adapter. `registry.PARITY` records the two measured name collisions: `mom_12_1` IS the same signal across cadences (spearman 0.996) but **`vol_trend_3m` is NOT** (spearman 0.58, 29% sign disagreements, opposite signs) — never merge them. Regenerate with `scripts/signal_divergence.py`.

**`routers/`** — one file per domain (flat: `admin`, `airs`, `auth`, `benchmarks`, `companies`, `earnings`, `exchange_fees`, `fx`, `indicators`, `ingest_runs`, `leonteq`, `longequity`, `scheduled_strategies`, `system`, `universe_templates`). Sub-packages: `momentum/` (`signals`, `backtest_crud`, `current_picks`, `backtest_stream/` SSE), `universe/` (`derive`, `derived_metrics`, `labels`, `screening`), `index_universe/` (`acwi`, `sp500`). `_auth_middleware.py` is the **API auth gate** (`enforce_api_auth`): EVERY `/api/*` request needs a valid Supabase JWT, role-gated — admins get everything; non-admins only the API behind their pages (reads: `/api/companies`, `/api/earnings`, `/api/airs`, `/api/usage`, `/api/scheduled-strategies` (filtered to `user_visible`), `/api/fx/`, `/api/benchmarks`, + the two read-only /schedule strategy-detail sub-resources `GET /api/momentum/current-picks/{id}` & `GET /api/momentum/backtests/{id}` — allow-listed by EXACT pattern, then each endpoint authorizes the id via the owning strategy's `user_visible`; writes: `/api/management-dashboard/parse` & earnings-refresh); anonymous → 401. Public tier (no auth): `/api/health`, `/api/hello`, the `*/cron` endpoints (self-check `X-Cron-Secret`). `/api/auth/*` is self-auth (the endpoint verifies its own token; admin user-mgmt calls `_require_admin`). Tokens are verified via `routers.auth.verify_token` (GoTrue `get_user`, cached 60s for polling). Role-resolution + the admin "view as user" preview share one helper — `routers/_authz.py::is_admin_request` (honors the `X-View-As: user` header `apiFetch` forwards from the `view_as` cookie); `scheduled_strategies._is_admin` + the momentum read gates all delegate to it so the preview can't desync. **All frontend API calls must attach the JWT — use `lib/apiFetch.ts` (and `runSSE` for SSE; never `EventSource`, which can't send the header).** `ingest_runs.py` is now just the HTTP layer (router + endpoints + `kick_off_refresh`/`_spawn_ingest` dispatch); the pipeline itself lives in `ingest/phases/` (see below).

**`ingest/`** — LongEquity + GuruFocus pipeline: `acquire` (download reports) → `flatten` (grouped Excel headers → flat DF) → `extend_primary` (primary exchange) → `transformation` → `load_into_supabase`; `resolve_tickers` (OpenFIGI), `prices` (daily closes + volumes from GuruFocus, cached in Storage; `_retry_transient` for timeout/5xx on Storage + `metric_data.upsert`), `staleness`, `api_usage`, `prune_companies`. **`ingest/phases/`** — the scheduled-refresh pipeline, split one module per phase so each is unit-testable in isolation: `runlog` (run-row tracking: `_Throttle`, `_create_run`, `_update_run`), `acquisition`, `templates`, `prune` (prune + dedupe), `prices` (+ company loaders), `momentum` (+ daily MTD), and `pipeline` (the three orchestrators — `_run_pipeline_sync`, `_run_daily_mtd_pipeline_sync`, `_run_daily_template_refresh_pipeline_sync`). `routers/ingest_runs.py` imports the orchestrators from here.

**`universe/`** — criteria-driven screening: `criteria` (definitions), `screen` (apply + store derived universes), `derived_metrics` (store metrics in `metric_data` source `derived`).

**`index_universe/`** — index reconstruction: `sp500` (Wikipedia history + OpenFIGI), `acwi` (iShares holdings + MSCI announcements), `templates/` (self-updating canonical universes — `ACWITemplate`, `LeonteqTemplate`; `_cache.py` LRU+TTL membership cache).

**`momentum/`** — backtester engine:
- `data.py` — bulk loaders (`load_universe`, `load_all_prices`, `load_all_volumes`), FX conversion, currency lookups. Queries batched in chunks of `IN_CHUNK_SIZE` (=200, `deps.py`) company IDs (Cloudflare 502 guard).
- `signals.py` — 5 price signals (mom_12_1, mom_6m, volatility_adjusted_return_6m, drawdown_from_recent_high_pct, above_200ma) + 2 volume (vol_20d_vs_60d, vol_trend_3m), each tagged `"group"` price/volume. Pre-indexed `dict[int, pd.Series]`. **Strict `<` cutoff** on `as_of_date` (never see the bar we trade). **30-day staleness guard** drops stale tickers.
- `scoring.py` — per-category 0-100 min-max normalized score, combined via adjustable category weights into `momentum_score`. `random_select` for the random baseline.
- `backtest.py` — three runners: `run_backtest` (monthly rebalance loop), `run_multi_trial_backtest` (N random runs, mean ± std), `run_current_portfolio` ("hold today" + per-trading-day daily picks with MTD return + turnover).

**`tests/`** — pytest (228 tests). Momentum engine (`test_signals`, `test_scoring`, five `test_backtest_*`) **plus** an ingest-data-logic suite added 2026-06-04:
- **Pure data-routing / dedupe** (no DB): `test_exchange_map` (the iShares↔GuruFocus resolution where the listing-misroute incidents live — Vienna≠Prague, override remap/rename/unavailable, HKSE pad, + the 10 historically-broken companies pinned as regression cases), `test_gurufocus_url`, `test_dedupe_canonical` (`canonical_ticker`/`canonical_name`/`exchange_priority`/`pick_winner`).

- **Frozen-only policy (2026-06-15)**: universes are listed frozen-snapshots-only EVERYWHERE selectable/browsable — `/backtest` + `/regime-detector` (useStaticUniverses), `/earnings` (`/api/earnings/universes`), `/universe` screener (`/api/universe/labels` filtered `frozen_at IS NOT NULL`), `/companies` memberships. The ONLY exception is `/longequity-universe`'s own per-month view. The management pages (`/acwi`, `/sp500`, `/leonteq`) still show their LIVE universe as the freeze *source* (you freeze a copy from there). **Leonteq freeze applies a market-cap floor** — settable from the `/leonteq` "Min cap €B" input (defaults to `LEONTEQ_MIN_MARKET_CAP_EUR` = €1B; passed as the `min_market_cap_eur` query param to the freeze endpoint, 0 disables): only companies with a known `market_cap_eur` ≥ floor are frozen in; below-floor or no-cap are dropped. A company with no cap that's **GuruFocus-UNSUBSCRIBED is dropped silently**, but a **subscribed** company with no cap is returned in the freeze result's `missing_market_cap` list (and shown on `/leonteq`) — a data gap to fix via "Refresh market caps" before re-freezing. All other freezes (ACWI/SP500/LongEquity) have no cap floor.

- **Add one row by ISIN** (`/asset-pipeline` → the ISIN box; `POST /api/asset-pipeline/store`) — resolves synchronously (OpenFIGI-anchored) and stores the price series, so the row lands complete rather than queued. **⚠ It 409s on an ISIN already in the grid and refuses to touch it, and that guard is load-bearing: RE-RESOLVING IS DESTRUCTIVE.** `resolve()` ranks Yahoo's candidates by `med_adv_eur` and would pick the right listing every time — but **Yahoo answers a search with an EMPTY list under load instead of a 429**, and a candidate set missing the real listing hands the win to a thin foreign line. Measured: a re-resolve of Alphabet Class A (`US02079K3059`) repointed it from **GOOGL** (€8.79bn ADV, 5,502 bars from 2004) to **GOOA.VI — Vienna** (€76,634 ADV, 2,302 bars): a **75,000× thinner** listing, silently, with no error. Same failure mode as the NVDA-on-Stuttgart bug, different road. Re-resolving is a deliberate act with its own control (the per-row Resolve action). Pinned by `tests/test_add_isin_guard.py`. Status codes: **409** already present (nothing done) · **422** new ISIN recorded but unresolved (the row IS there, unmapped) · **429** Yahoo throttled · **502** real fault.
  **⚠ A ZERO-BAR RESOLUTION IS NOT A RESOLUTION** (`store_one`, same guard file). Ten distinct **Leonteq structured products** (CH ISINs, Guernsey branch) each resolved to the SAME symbol `GODE.DE` — `bars=None`, `price_from=None` — and each was written `status='ok'`. Yahoo has no listing for a structured product, so its search returns a name-alike, the ranker takes it (nothing better on offer), and ten unrelated instruments end up pointing at one empty series: ten confident rows, zero data, no error. `store_one` now records such an ISIN as **unmapped** and raises, rather than keeping a mapping that only looks like one.
  **⚠ AN ETF MUST BE REPOINTED BY ISIN, NEVER BY NAME** (`scripts/repoint_etf_listing.py`). `repoint_primary_listing.py` cannot do it: it detects on **ADV ÷ market cap** and filters `asset_class == 'equity'`, and **a fund has no market cap** — so it reports zero candidates over a grid full of thin ETFs. But the obvious fix (point `resolve()` at them) is *worse than the disease*: `resolve()` searches Yahoo **by name** and gates identity with `same_company()`, which strips corporate forms — right for an operating company, **dangerous for a fund**, because a fund's share classes have near-identical names and DIFFERENT ISINs. Both of these are in the grid: `IE00BNDS1P30` → V3GF.MI and `IE00BNDS1Q47` → V3GE.DE, *both* named "Vanguard ESG Global All Cap UCITS ETF". They differ by accumulating/distributing, which no name comparison survives — and an Acc class rolls dividends into the price while a Dist class pays them out, so the two **compound differently**. Swapping them isn't a venue annoyance, it's a **wrong price series**. So candidates are enumerated from **OpenFIGI's listings of the one ISIN** (`openfigi.lookup_isin` → `build_candidates`), which by construction contains only the venues *that share class* trades on — the safety is **structural, not a heuristic** (measured: `IE00BNDS1Q47` yields `V3GE.AS/.MI/.DE` and never V3GF). The name check that remains guards the *other* failure — `build_candidates` **constructs** `ticker + venue suffix`, and tickers are reused across venues, so a constructed symbol can land on an unrelated instrument. Pinned by `tests/test_etf_repoint.py`. **⚠ A `queued` FUND HAS NO ANCHOR AT ALL** (2026-07-14) — `--isin` now reaches a row of any status (a queued ETF has *never* been resolved: no symbol, no prices, invisible everywhere, and it is the row that most needs an ISIN-anchored resolve — `IE00BP3QZ825` iShares Edge MSCI World Momentum sat queued). But `_same_fund` gates against the **incumbent's Yahoo name**, and a queued row has none; its other two names are *both* vowel-crushed the way `_same_fund`'s docstring warns (OpenFIGI **and** Leonteq agree on `ISHR EDGE MSCI WRLD MOMENTUM`, against Yahoo's `iShares Edge MSCI World Momentum Factor UCITS ETF`), so anchoring on either rejects every candidate including the right one. The answer is **structural, not a looser matcher**: candidates all come from OpenFIGI's listings of the ONE ISIN and a fund's venues name themselves near-identically *to Yahoo*, so the anchor is their **CONSENSUS** (`_consensus_anchor`) — a constructed ticker that collided with an unrelated instrument is the outlier agreeing with nobody, and **a lone candidate is not a consensus** (that is an unchecked guess, refused). Measured: 6 venues validated, `IS3R.DE` €5.63m/day chosen over `IWFM.L` €1.45m/day (the LSE lists this share class **twice** — `IWMO.L` USD and `IWFM.L` GBp). Counting those would push ~20% of a portfolio into a phantom sector and deflate every real one — so a fund goes into ONE **`Fund (not looked through)`** bucket on **all three** axes. A 40%-ETF portfolio shows a 40% bar meaning *"we cannot see inside this"*, which is true and beats a confident invented split. Cash is a bucket too (its drag is a fact); an unclassifiable holding is `Unclassified`, never dropped.
  - **⚠ REGION IS THE ISSUER'S, NOT OUR VENUE'S — THE S&P 500 IS NOT 7% EUROPEAN.** `asset_grid.msci_region` comes from `geo.resolve_geo`, which **falls back to the LISTING country when the domicile is unknown** — sane for the instrument grid, catastrophic here. Yahoo returns no domicile for a thin German regional line, and our grid prices US megacaps on exactly those: **`LLY.SG` Eli Lilly on Stuttgart (€873bn), `CHV.DU` Chevron on Düsseldorf, `IBM.HM` IBM on Hamburg** — all inherited "Germany" → **Europe**. 54 members were classified Europe (**7.2%** of cap). `_region()` now goes **domicile → the ISIN's own country prefix → `Unclassified`, never the listing**: 20 members, **2.1%**, and those are *real* (Linde, Eaton, Accenture, Medtronic, Trane, Johnson Controls = Irish; Chubb = Swiss; NXP = Dutch — the S&P genuinely holds foreign-domiciled constituents). **The job is to lose the 5.1%, not to force the index to 100% American.** Known limit: an ADR carries a US ISIN, so a *domicile-less* ADR reads North America — it only bites when Yahoo gave no domicile at all, which for an ADR it usually does.
  - **⚠ CURRENCY IS THE COMPANY'S, NOT OUR VENUE'S.** By *listing* currency the S&P 500 reads **91% USD**; by `market_cap_currency`, **98%**. The gap is **40 of 491 members our grid prices on European/Canadian venues** (Corning on Stuttgart, Ciena on Xetra, WR Berkley on Munich, Exxon on a Canadian line) — the wrong-listing bug, **inside the benchmark**. Pricing Corning off Stuttgart does not make it a euro asset, and the naive chart called the S&P *"12% EUR"*. Fixed by reading the reporting currency, and the mismatch is **counted and surfaced** (`benchmark_foreign_listings`) rather than absorbed — it also means **the benchmark's PRICE SERIES is drawn off those venues**. Benchmark weights come from `_benchmark_index._members` (already deduped — GOOGL+GOOG would double-count Alphabet's cap, 11.3% of the index, fictional); they are never re-derived.

  **Palette: computed, not eyeballed.** The app's standard A/B pair (accent blue + `compare` violet) **FAILS** colourblind separation — ΔE **4.9** under deuteranopia, i.e. one colour. Blue + `warn` amber scores **103**. Run `dataviz/scripts/validate_palette.js`, don't reason about it. The amber sits a hair under 3:1 contrast on white, which obliges relief, so every bar carries a **direct value label** (in ink — text wears text tokens, never the series colour). Pinned by `tests/test_airs_portfolio_analysis.py`. **Expanding a row adds the ARITHMETIC BEHIND its YTD** — five per-holding columns on the positions table (`Start (€)` · `Start date` · `End (€)` · `End date` · `Return (€)`, from `compute_holding_marks`, attached in `_shape_positions` and **never cached** — a price mark is true for one day, the composition it prices is not). Each holding is bought at its last close on or before the window and held to its latest close; **weighting the `Return (€)` column by the model's percentages reproduces the row's YTD exactly** (measured: AITopSelectie OFF FX, 51.4812% both ways), because both read the same EUR series through the same anchor — `ytd_anchor_for()` is the **ONE** definition of that anchor, shared by both, so the entry prices printed under a +51.48% cannot belong to a different window than the number they explain. ⚠ **The prices are in EUR, not the listing's currency** — `return_pct` is an EUR return and carries the FX leg, so printing the native closes as the arithmetic would show two numbers whose ratio is not the third (a USD holding rises in dollars and falls in euros on the same days); the native close + currency ride along as the **tooltip** (`*_price_local`), never as the sum. **End dates differ per holding** — vendors publish unevenly, so a lagging name is marked at its last known close and the date says so. **⚠ A SPARSE SERIES GETS AN INTERPOLATED OPENING MARK, AND IT SAYS SO** (`_mark_at`): a close within `_MARK_GAP_TOLERANCE_DAYS` (7) before the anchor **IS** the anchor's price (31 Dec is the 1 Jan mark — interpolating there would replace every observed opening price with a modelled one), but when the series has no price near the date and real closes **bracket** it, the opening value is **linearly interpolated** between them and flagged (`start_interpolated`, `start_gap_days`; ⚠ + `(est)` in the row, `≈` on the portfolio's YTD, `interpolated_holdings` in the payload). Beyond `_MAX_INTERP_SPAN_DAYS` (400) it is **refused** — straight-lining across more than a year is invention, not estimation (same refusal as `_trailing_12m`'s 450-day cap) — and a series that *ends* before the window is never **extrapolated** forward. `_index` and `compute_holding_marks` both mark through `_mark_at`, so the itemised rows still weight to the portfolio figure exactly. ⚠ **The load window is a PERFORMANCE bound, never a correctness one** — `_prepend_opening_bars` fetches the opening bar however far back it sits, and the FX window is then widened to reach it (`fx_from`), because a bar with no rate on or before it is silently dropped by `_eur_series`. It *was* a correctness bound until 2026-07-14: iShares Euro HY (`IE00B66F4759`) is mapped to **`ISHHF`, a US OTC line with 54 bars in TEN years**, whose last close before 1 Jan was 2025-11-03 — 14 days outside the expanded row's 45-day lookback. The row showed a blank while the portfolio figure, loading from the earliest inception, priced the same holding at **23.6% weight**. Two windows, two answers, no error. **The interpolation is a mitigation, not the fix — that ETF is on the wrong listing** (`scripts/repoint_etf_listing.py`, by ISIN). No marks at all for cash (no ISIN, no series — it is priced at a flat 0% *inside* the portfolio figure), an unresolved ETF, or a holding that had not listed when the window opened; a `0%` there would be a claim, not a blank. **Sortable `Resolved` column** — how many of the model's instruments we can actually price, i.e. have a **Yahoo (`asset_price`) series** for. It reconciles **exactly** with `Holdings` (`resolved_holdings + unresolved_holdings == holdings`): both count **DISTINCT ISINs** (a model may list one instrument twice — VTopSelectie OFF FX holds CapitaLand at 2% *and* 3%, so counting rows would report 29 resolved of 28 held) and both **exclude cash** (no ISIN, not an instrument — `priced_holdings` is the cash-inclusive leg count and is a *different* number). Shown `n/m` in amber whenever short, because the gap IS the weight the returns are renormalised over — and it is the **visible cause of an `n/a` row**: BUS_Alternatives_FX holds 9, prices 5, and its missing 45% is three ETFs still `queued` in the grid (Global X SuperDividend, YieldMax, WisdomTree — fixable with `scripts/asset_resolve_missing.py`) plus an in-house fund with no listing at all (permanently unpriceable), so coverage is 55%, under the floor, and every figure is refused. Absences never look like zeros: `n/a` = unpriceable, `—` = window too short / denominator undefined (a curve that never fell has no downside deviation — Sortino is *undefined*, not infinite), and a **no-model** row shows `—`, not the `…` a loading row wears. **"Hide small portfolios"** (checked by default) is a **KEEP rule** — it shows only the rows with a counted model holding **> 5** instruments (42 of 95), so the single-instrument wrappers *and* every row with no countable model (no fixed model, no snapshot, count failed) are all hidden together; unchecking restores all 95. Pinned by `tests/test_airs_portfolio_perf.py`. **Instruments** is the flat per-ISIN grid (`asset_grid` view, TanStack virtualized, all rows client-filtered). The three rightmost columns — **Exchange · Ticker · Div/share** (`GURUFOCUS` source badge) — are the only ones not sourced from Yahoo/OpenFIGI/Leonteq. **TWO bridges reach GuruFocus** (`routers/_asset_dividends.py`, the ONLY place the two entity universes meet), and which one a row takes decides what data it can have:
  - **company-backed** — ISIN → `company.isin` → `gurufocus_ticker` → `metric_data`. Equities we ingest (~13% of rows). Has the fiscal-period series (`financials`) **and** the payment feed.
  - **listing-backed** — ISIN → GuruFocus's undocumented **`isin/{ISIN}`** → `[{symbol, exchange}]`, cached in **`gurufocus_listing`** (migration `20260713000000`). This is the ONLY bridge an **ETF** can cross — no ETF is ever ingested into `company`, so before this the whole 87% tail (ETFs, crypto, commodities) showed `—` even though GuruFocus has the data (QQQ: 89 per-share distributions). An ETF has **no `financials` blob**, so the payment feed IS its dividend history — the modal hides annual/quarterly rather than showing them empty. Its payouts are **distributions** (can include return of capital / capital gains), not only dividend income.

  **Picking the listing (`_gf_listing.py::pick_listing`) is about COMPLETENESS, not currency.** `isin/{ISIN}` returns EVERY listing worldwide — Apple comes back with **19** (Vienna, Sofia, Zurich, Frankfurt, Stuttgart, Milan, Kazakhstan, Mexico…), and filtering to `FEASIBLE_GF_EXCHANGES` still leaves it on Zurich, Xetra, Milan, Warsaw *and* Nasdaq. The intuitive fear — "a Xetra line reports Apple's dividend in EUR" — is **measured and FALSE**: GuruFocus reports a dividend in its **declaration currency on every listing** (Apple 2026-05-11 = `0.27 USD` on Nasdaq, Xetra, Zurich and Milan alike, ratio 1.0000). Same ISIN = same share class = one economic dividend. So a foreign listing is *not* a wrong-number hazard, and the EUR panel is the usual pay-date conversion. **What the listings differ in is HISTORY LENGTH**: 91 → 82 → 63 → 35 records, and Zurich's jumps 2026-02-09 → **2021-02-05** (~16 quarterly payments missing from the middle). That is dangerous because it's silent — `_trailing_12m` infers `k` from the median ex-date gap and would sum "the last 4 payments" across a five-year hole into a confident, plausible, fictional annual dividend. So: candidates are scored against the asset row (+1 currency, +1 ticker), the **best** one is taken (ties break toward a US listing — GuruFocus's deepest feeds), score 2 ⇒ `is_home`. A non-home listing still charts (`is_home=false` → amber ⚠ on the Ticker cell + a modal banner), and **`_trailing_12m` returns `None` whenever its window spans > `_TTM_MAX_SPAN_DAYS` (450)** rather than summing across a gap. Only `not_found` / `unsubscribed` refuse, both **negative-cached** so a dead ISIN is never re-billed. Pinned by `tests/test_gf_listing.py` against the real API responses. (An accumulating ETF like iShares Core MSCI World, `IE00B4L5Y983`, correctly returns **zero** payments — `OTCPK:IRRRF` has none, because an Acc fund distributes nothing.)

  **Two exchange-code spaces, and the US one is a minefield.** GuruFocus's own `exchange_list` puts NINE codes in region USA: `NAS · NYSE · OTCPK · OTCBB · AMEX · ARCA · IEXG · BATS · GREY`. Two traps: (1) the `isin/` endpoint says **`NAS`** while `gurufocus_exchange`, `_build_symbol` and `FEASIBLE_GF_EXCHANGES` all say **`NASDAQ`** — bridged by `GF_EXCHANGE_ALIASES`; (2) **`ARCA` (NYSE Arca) is where most US ETFs actually list** — of SPY/IWM/VOO/XLU/EDV/GLD/QQQ, **six are ARCA** and only QQQ is NAS. `ARCA`/`BATS`/`IEXG` are now in `FEASIBLE_GF_EXCHANGES` (+ a USD fallback in `_gf_listing._US_EXCHANGES`, since they have no `gurufocus_exchange` row). Omitting ARCA didn't just lose coverage — it **mis-resolved**: SPY and GLD *also* list on SGX, which IS subscribed, so an unknown ARCA silently handed back the **Singapore** line of SPY. If a US ETF reads UNSUBSCRIBED, this code space is the first place to look.

  Exchange + Ticker are the two halves of the `EXCHANGE:TICKER` symbol the dividend fetch queries (both ride along in the `/dividends/coverage` payload — no extra request), and can differ from the yfinance Symbol: separate id spaces, joined only by ISIN. **Every dead end names itself** — the Div/share cell never renders a bare blank, because for a payout a blank reads as "pays nothing", which is usually false. The **same states for a stock and an ETF**: `Fetch` (never resolved) · **NOT EQUITY** · **NO LISTING** · **UNSUBSCRIBED** · **NO DATA** · **NO PAYOUTS** · `View`. Three of those are load-bearing distinctions, not synonyms:
  - **NOT EQUITY** (`not_applicable`) — a bond / future / FX ISIN can never name an equity listing, so **no API call is spent**. `_NON_EQUITY_PRODUCTS` short-circuits on `leonteq_product_type`. This is **30% of the grid** (4,877 BONDS of 16,150 rows, + 410 futures): a full backfill was buying ~5,300 "not found"s. `FUNDS` is deliberately NOT skipped — a "fund" may be an ETF GuruFocus carries, and guessing wrong blanks a row that has real data. A bond pays **coupons**, not a dividend per share; the question doesn't apply.
  - **NO PAYOUTS** (`has_payments=false`) — an *answer*. GuruFocus returned `[]`: an accumulating ETF (iShares Core MSCI World) or a non-paying stock (Berkshire) genuinely distributes nothing. Three-valued on both sides (`gurufocus_listing.has_payments` / `company.has_dividend_payments`), `NULL` = "never looked", so it can't collapse into "there is nothing to find".
  - **NO DATA** (`no_data`) — a *gap*. GuruFocus returned **`null`, not `[]`** — it has no dividend record for that symbol, typically a dead OTC line of an acquired company (Micro Focus → `OTCPK:MCFUF` after the OpenText takeover). Saying "pays nothing" here would be a claim we can't make. (This used to raise a **502**, blaming our server for a delisted ticker.)

- **`/management-dashboard` → Benchmarks table** (`BenchmarksPanel.tsx` → `GET /api/benchmarks/index/{label}` → `routers/_benchmark_index.py`) — a cap-weighted index **rebuilt from our own membership + prices + FX**, so a benchmark number is computed the same way a portfolio's is and the two are comparable. Currently the `SP500` universe (493 real constituents from the Wikipedia reconstruction, not "the 500 biggest US companies" — the S&P is committee-selected). **Validated: 2026 YTD = +9.10% USD against SPY's +9.02%** (SPY is in `benchmark` with 7,168 bars back to 1998 and *is* the index — this exists for comparability, not to replace it). Three traps, each of which alone yields a plausible-looking wrong number (measured: **+21.70% / +5.95% / +9.10%**):
  - **⚠ THE WEIGHT IS AS OF THE START OF THE PERIOD.** Weighting a YTD return by **today's** market cap is look-ahead bias — a stock that doubled has ~2× the cap it started with, so today's cap retroactively hands the winners a share of the index they never had. Measured, that alone turns +9.10% into **+21.70%**. Start weight is recovered as `cap_start ≈ cap_now × (price_start / price_now)` (the share count is what stays put; the price carries the cap). Equivalently: buy-and-hold of the start-of-year basket, which is exactly what a cap-weighted index fund does.
  - **⚠ OUR STORED CLOSES ARE NOT SPLIT-ADJUSTED AND CANNOT SELF-HEAL.** `ingest/prices.py` only fetches dates *newer* than what we hold, so when the vendor rewrites history for a split we never re-read it and the pre-split prices sit at the old scale for ever. **3 of 493 S&P names in 2026 alone**: KLA `1929.20→210.81` (9:1), CrowdStrike `763.14→193.19` (4:1), DuPont `48.19→140.01` (1:3 reverse). It hits the index **twice in the same direction** — the start weight is backed out through the same broken price, so a 9× bogus ratio inflates the weight by 9× *and* fakes an −89% return (KLA read −80.6% at a 2.70% weight it never had). `_split_adjust` rescales, **but only when the jump matches an explicit whitelist of real split ratios** — "any small rational n/d" is dense enough to sit within 5% of anything and would "correct" a genuine −45% crash into nothing (a test caught exactly that). Known limit: a 2:1 split and a stock that halves are numerically identical, so **every adjustment is surfaced in the payload + UI, never silent**. ⚠ **This is a patch, not the fix — the same rows feed the momentum signals.**
  - **⚠ ONE COMPANY, ONE ROW.** GuruFocus puts the **full company market cap on every share class**, so Alphabet (GOOGL+GOOG) contributes €3,785bn *twice*. Over a top-500-by-cap pool that was €7,683bn of €67,863bn — **11.3% of total weight, fictional**.
- **Income-statement columns** — **Revenue** · **Gross profit** · **EBIT** · **D&A** · **Interest expense** · **Pretax income** · **Income tax** · **Net income** (`routers/_asset_financials.py`, `GET /api/asset-pipeline/financials/isin/{isin}/{item}`). A **bank** charts everything except **Gross profit + EBIT** (both N/A) — a mix only expressible because `_has_line` asks per-LINE, never per-template. Sign conventions differ per line and are charted **as reported, never flipped**: Interest expense and Income tax come back **negative** (outflows), D&A **positive** (a magnitude). **Each entry names its `section`** (`income` default · `cashflow` · `balance`), each with both schema spellings — **Operating CF** (`Cash Flow from Operations`) and **Capex** (`Capital Expenditure`) come from the cashflow statement. Capex is **not** `Purchase Of Property, Plant, Equipment` (Mitsui: PP&E −128,242 vs capex −137,759 — capex also picks up intangibles); the mapping is proven by the identity **OCF + capex = Free Cash Flow** (Apple: 111,482 − 12,715 = 98,767, matching GuruFocus's own FCF line). That isolation is load-bearing: the cashflow statement carries its own `Cash Flow Depreciation…`, identical in value to the income statement's D&A, and explicit sections stop either being read from the wrong place. **Operating CF's sign is INFORMATION, not a convention** — Apple `+111,482`, JPMorgan **`−147,782`** (a bank's operating cash flow routinely goes negative as loans and trading assets grow), so it is deliberately NOT in the frontend's `NEGATIVE_BY_CONVENTION` set; claiming "this line is reported negative" would be false for half the companies. **EPS LTG is a SCALAR — no series at all.** The analysts' long-term EPS growth consensus is ONE number (`long_term_growth_rate_mean`: Apple ~13, NVIDIA ~47, JPMorgan ~8.7), and GuruFocus publishes it as one. Inventing a date so it could be plotted would dress a single point up as a trend, so the response carries `scalar_value` (with `annual`/`quarterly` empty) and the modal shows the **number**, with no cadence toggle. `_estimate_scalar` **refuses to read a list** — taking `[0]` off a series would silently report the first forecast year as though it were a long-run rate. Its two lookalikes are NOT it: `future_per_share_eps_estimate_growth` (the CAGR the estimate series implies) and `future_eps_nri_estimate_growth` — Apple's three are 13.01/13.03/13.01, indistinguishable by eye, and **NVIDIA is where they diverge** (47.57 vs 45.72).

  **Est. revenue growth is DERIVED and is a PERCENT** — the case the ratio ban pointed at, now implemented rather than banned. GuruFocus's own `future_revenue_estimate_growth` is a **scalar** (Apple 10.09, NVIDIA 45.73), one long-run rate — nothing to plot — so `_yoy_growth_series` computes the year-on-year step from `revenue_estimate`, **anchoring the first forecast year on the last REPORTED revenue** (Apple: est FY2026 477,600 vs actual FY2025 416,161 = **+14.7%**; NVIDIA **+82.0%**). It reads BOTH blobs for that anchor. If the reported period doesn't strictly *precede* the first estimate the base is ignored, never used to compute growth across an overlap.

  **Each entry declares a `unit`** — `millions` (default) · `per_share` · `shares` · `percent`. **`shares` changes BEHAVIOUR, not just labels**: a share count (Apple 15,004.697M) is not currency, so it is excluded from `_CURRENCY_UNITS`, the EUR conversion is **skipped** (`value_eur` stays null) and the modal renders **ONE** chart — an empty second panel would imply a conversion that cannot exist. This is the "skip the conversion, don't relabel it" case the ratio ban warns about, now implemented. Shares outstanding is the **diluted average**, the same basis as EPS, which is what makes them tie (Apple 7.46 × 15,004.7 ≈ net income 112,010; NVIDIA 4.90 × 24,514 ≈ 120,067) — a cheap cross-check that both fields are right. **EPS (diluted) is the only per-share column** (Apple 7.46 USD/sh, ties out as 112,010M ÷ 15,004.7M shares), and rendering it on the millions path turns $7.46 a share into "$7.46 million" — off by 1e6 and utterly plausible. Both units are *currency*, so `value_eur` stays valid for both; only the scale + axis label change. Note `EPS (Diluted)` does **not** contain the string "per Share", so a field-name sniff would wave it through — **the unit must be declared, never inferred**. **Ratios (`… %`) remain banned outright**: `_convert_to_eur` divides by an FX rate, so a percentage would come back "13.3% in EUR". A ratio needs the conversion *skipped*, not relabelled. Income tax is GuruFocus's **`Tax Provision`** (there is no "Income Tax" key). **Two lines are the SHAREHOLDERS' variant, and each has a tempting "total" sibling that includes minority interest** — `Net Income` (not `Net Income Including Noncontrolling Interests`) and **Equity** = `Total Stockholders Equity` (**not** `Total Equity`: Mitsui reports 864,727 + minority 124,057 = 988,784). In *both* cases **JPMorgan's two figures are identical** (zero minorities), so validating on JPM alone blesses either choice. **Net income is the SHAREHOLDERS' line, not `Net Income Including Noncontrolling Interests`** — so `pretax + tax` deliberately does NOT tie to it for a company with minorities (Mitsui FY2025: 68,608 − 21,698 = 46,910 = the Including-NCI figure, while `Net Income` = 34,378; the 12,532 gap is minority interest). JPMorgan's two are identical (57,048), so checking against JPM alone would bless either choice — same shape as the EBIT/Operating-Income trap. **A multi-field entry declares `combine`, and getting it backwards is a real bug**: `sum` adds *components* (**Total debt** = short-term + long-term — GuruFocus has no "Total Debt" line), `first` coalesces alternative *spellings* of ONE line (**Cash & equiv.** — GuruFocus renames it per template: `Cash and Cash Equivalents` for most, `Balance Statement Cash and cash equivalents` for a **bank**, which has neither ordinary key). Summing spellings double-counts; coalescing components halves. Cash is the **narrow** line — *not* `Cash, Cash Equivalents, Marketable Securities` (Apple: 54,697 vs cash-only 35,934).

  **Forward EPS is a FORECAST from a second SOURCE** (`source: "estimates"`) — `stock/{sym}/analyst_estimate`, **SINGULAR**; the plural is one of the fake endpoints that 200s with the router-fallback payload (same trap as `dividend`/`dividends`, pinned in `gurufocus_api.json`). Different shape (`{annual,quarterly}` with **compact `YYYYMM`** dates, *not* the financials blob's `2025-09`), and some values in that dict are **scalars, not arrays** (`long_term_growth_rate_mean`) — a parser that assumes lists raises. It's `per_share_eps_estimate`, not `eps_nri_estimate` (Apple 8.76 vs 8.77 — near-identical, so eyeballing one company can't choose). Every date is in the **future**, so no FX rate exists: the EUR line forward-fills to the **latest known rate**, which is the only honest option but means it carries *today's* FX assumption — the modal says so. An uncovered company has no estimates at all (a fact about coverage, not a gap in its accounts).

  **Total debt is COMPUTED** — the entry declares `fields` (a list) instead of `field` and `_summed_series` adds short-term + long-term debt off the **balance sheet**. It uses the **"& Capital Lease Obligation"** variants because they're the only keys a **bank** has (JPMorgan lacks the plain `Short-Term Debt` / `Long-Term Debt`), and for everyone else the two spellings are identical. A period where one component is missing is **dropped, never summed as if it were zero** — an understated debt that looks like a real number is worse than a gap. A derived series carries a `note` and the modal prints it: **a computed number must say it was computed.**

  **⚠ Never add a `… %` or `… per Share` line to `_ITEMS`** — every entry is assumed to be a currency amount in MILLIONS and gets FX-divided, so `Tax Rate % = 15.61` would render as "15.61M USD = 13.3M EUR". GuruFocus sits `Tax Rate %` directly beside `Tax Provision`, so it's one typo away; pinned by a test. Same ISIN→listing bridge, same two charts (native + EUR). **A column is a `_ITEMS` registry entry, not a module** — one endpoint, one modal, one blob. `financials.json` carries EVERY line, so every column after the first on a company is **free**, and the cache is shared with the earnings pipeline. Each entry carries `field` (GuruFocus's key), `label`, and `phrase` — the last because `label.lower()` renders EBIT as "ebit". Two per-line gotchas: **EBIT is GuruFocus's own line — never substitute `Operating Income`** (Mitsui Chemicals: EBIT `85,035` vs Operating Income `56,602`, while Apple's two are *identical* at `133,050` — exactly how you'd convince yourself the swap is safe); and **Interest expense is reported NEGATIVE** (an outflow: Apple `−3,933`, JPMorgan `−101,350`) and is charted **as reported, never sign-flipped** — a `0` is a real value (Apple nets it out), not a hole; only `""` is dropped. **Values are in MILLIONS.** Five traps, all measured:
  1. **GuruFocus FX-converts financials into the LISTING's trading currency, per fiscal period** — the *opposite* of the dividend feed. A non-home listing gives a genuinely different number (CSX FY2025: `14,092 USD` on Nasdaq vs `12,034.568 EUR` on Xetra). `summary.company_data` distinguishes `currency` (trading) from `currency_comp` (reporting).
  2. The fiscal axis ends with the literal **`TTM`** — not a date, and it duplicates the latest period. Dropping the label but keeping the value shifts every figure one period.
  3. The **quarterly block's axis is ALSO called `Fiscal Year`**, not "Fiscal Quarter" — assume otherwise and every quarterly series is silently empty.
  4. **GuruFocus renamed the sections** (`income_statement` vs the cached `"Income Statement"`), and Storage holds **both**, so `_SECTIONS` tries each. Cached blobs also run **newest-first** while live ones run oldest-first (both with TTM last) — labels and values share the order, so `zip` is safe; don't "fix" it by reversing one side. ⚠️ The rename is a **latent bug in `ingest/earnings/financials.py`**, which derives its `metric_code`s from those names — see [`TODO.md`](TODO.md).
  5. **A BANK has no gross profit line at all.** JPMorgan's `ind_template` is `'B'`: it reports Interest Income / Net Interest Income and has no cost of goods sold, so the key simply isn't there. That's an **answer** (`applicable=false` → "N/A", naming the template), not a data gap — badging it NO DATA would claim a missing number that doesn't exist. `_has_line` distinguishes *absent* from *present-but-empty*.

## UI Design System

Single fixed theme: **"Azure Blanc"** (LIGHT) — porcelain-white surfaces, deep-navy ink, a sky-blue accent, over a faint azure gradient-mesh background; frosted-white chrome (sidebar + floating menus), *solid* white data surfaces so dense tables/numbers stay crisp, soft azure button glow. No theme switcher — the whole palette + treatment lives in `frontend/app/globals.css`'s `@theme` block + the few "Glass treatment" rules under it; charts mirror it in `lib/chartTheme.ts` (light grid, white tooltips). **Everything routes through these `@theme` design tokens** — never inline hex or raw Tailwind colour names (`gray-*`, `white`, `indigo-*`, …). Codemods tokenized ~250 surface literals + ~1,000 named-colour classes + ~2,000 grey/white classes. To re-skin, edit token values in `globals.css` (+ `chartTheme.ts`); nothing else. **Polarity note:** this is a light theme — `fg-*` runs dark→light (`fg-strong` = darkest ink); `neutral-*` are mid-slate RGBs used at low alpha (`border-neutral-800/40`) so soft borders still read on white; accent **400** is the on-white text/link blue (darker than the **500** brand), **600** is the button fill (white text); `overlay` is navy ink (hover wash darkens on white).

## Key conventions

- Backend wraps blocking Supabase calls in `asyncio.to_thread()`. SSE for long ops (ingest, scanner, backtest, current portfolio), with `: keepalive\n\n` comments before long work to beat proxy timeouts.
- **Live dashboards use SSE, not polling** (2026-07-01). `routers/_sse_stream.py` turns "compute the current payload" builders into ONE push stream that re-emits a topic only when it changes (frame = `{topic,payload}` inside `data:`, since the frontend `runSSE` only parses `data:` lines): `snapshot_stream_response` (multi-topic, per-topic recompute intervals — fast while a run's active, slow idle), `status_stream_response` (single `{running}` status, closes when done), `run_detail_stream_response` (one `ingest_run` until terminal). Endpoints: `/api/schedule/stream` (the /schedule activity card's 7 topics), `/api/usage/stream` (ApiUsageBadge), `/api/ingest/runs/{id}/stream` + `/api/companies/{market-cap/refresh,openfigi/verify}/stream` (the transient job-watch UIs). Frontend: **`lib/hooks/useEventStream.ts`** (multiplexed consumer — opens on mount + tab-visible, **closes when hidden**, reconnects with backoff, sets `failed` after N fails so callers fall back to polling) and **`lib/watchRun.ts`** (`watchRun(id, onUpdate, signal)` streams one run to completion). Every migrated surface keeps its `usePollingFetch` path as an automatic fallback (enabled only when `failed`), so SSE issues degrade to polling, never breakage. `usePollingFetch` itself now also pauses while the tab is hidden. Net: an idle /schedule tab makes **zero** requests (was ~10/min).
- AIRS portfolio data is parsed server-side, cached client-side in localStorage (no DB).
- Company deletion cascades: removes `metric_data` + `portfolio_weight` first.
- **The GuruFocus legacy API never 404s** — `stock/{sym}/<anything>` returns HTTP 200 and a 46-point all-zero series for any unrecognised sub-path, so `stock/AAPL/news`, `splits`, `guru`, `segments`, `profile`, `valuation`, `rank`, `earnings`, `indicator_price`, `analyst_estimates` all *look* like working endpoints and are not. **Always probe against a canary sub-path.** The catalogue of what actually works lives in [`docs/gurufocus_api.md`](docs/gurufocus_api.md) + `backend/gurufocus_api.json`, regenerated by `scripts/gurufocus_catalog.py` (responses cached in gitignored `backend/.gurufocus_cache/` → a re-run costs 0 API calls; `--max-calls` caps the spend). Pinned by `tests/test_gurufocus_catalog.py`. It has **no official documentation** — `gurufocus.com/api/overview` documents a *different, newer* product our key doesn't authenticate against. Undocumented but real and load-bearing: **`isin/{ISIN}`** and **`cusip/{CUSIP}`** → `[{symbol, exchange}]` for every listing worldwide, and **`exchange_list`** → `{region: [codes]}`. **`stock/{sym}/dividend` (singular) is per-share; `dividends` (plural) is cash-flow-for-dividends in $ millions, negative** — not the same thing.
- **Never compare company names with a raw `_name_score >= _NAME_MATCH` floor** — use `asset_pipeline.resolve.same_company()`, which strips corporate forms first. `rapidfuzz.token_set_ratio` scores `"NVIDIA Corporation"` vs OpenFIGI's `"NVIDIA CORP"` at **75.9** (floor 80), `"Intel Corporation"`/`"INTEL CORP"` at 74.1, `"Eli Lilly and Company"`/`"LILLY(ELI) & CO"` at 50.0. Until 2026-07-10 `resolve()`'s OpenFIGI name anchor used the raw floor, concluded the most-liquid `NVDA` was a *different company*, and swapped in `NVD.SG` — Stuttgart, EUR, €1.6M median daily traded value against Nasdaq's €28,076M. `identity_status()` always used `same_company`; the anchor was the odd one out. Pinned by `tests/test_asset_resolve_anchor.py`. To find the same class of defect elsewhere use **median daily traded value ÷ market cap** (`< 1e-5`; median is `4.6e-3`) — NOT an exchange-code map (Vienna≠Prague) and NOT "ISIN country ≠ listing country" (that flags every deliberate ADR→ordinary mapping). `scripts/repoint_primary_listing.py` does this; ~302 rows still flagged. **⚠ A MISSING MARKET CAP IS A SIGNAL, NOT A REASON TO SKIP** (2026-07-14): the ratio needs a cap, so a row without one was passed over — but **a dead listing is precisely what reports no cap**, so the rows most likely to be wrong were the ones the detector never looked at. Brown & Brown (`US1152361010`) sat on **BTW.DE** (Xetra, EUR, **€7,836/day, no cap, NOT ONE PRICE BAR**) while NYSE `BRO` does **€154m/day — 19,698×**; `--isin`, documented as "bypassing the ratio filter", still tripped over the cap the ratio is *computed from* and reported "0 candidates". Both fixed: `--isin` bypasses the cap too, and `--no-cap-max-adv 1e6` sweeps the blind spot (**221 equity rows have no cap; 112 trade under €1m/day** — Pool Corp on Milan at €1,042/day vs `POOL` at €142m, **136,740×**). **⚠⚠ BUT THAT CAP CHECK WAS ALSO, BY ACCIDENT, THE FENCE KEEPING FUNDS OUT OF A NAME-BASED RESOLVER** — funds report no cap (**all 29 ETP rows**), so removing it immediately produced `JE00BN7KB557` **WisdomTree Coffee** (an ETC on coffee futures) → **`LKNCY`, Luckin Coffee Inc**, a Chinese coffee *retailer*: `same_company("Luckin Coffee Inc", "WT COFFEE")` is **True** (token_set_ratio exactly 80.0 — the word "coffee" carries it), and nothing downstream would catch it because LKNCY is real, liquid and priced. The fence is now **explicit and structural** — an **allowlist** `_NAME_RESOLVABLE_TYPES` (Common Stock/ADR/GDR/REIT/…; unknown type ⇒ refused, and **no `openfigi_name` ⇒ refused**, since the identity gate is `if figi_name and …`, i.e. no name = *no gate*), it holds even under `--isin`, and refusals are printed, never silent. Closed-End Funds mostly *do* have a cap, so the hole predated the sweep. A fund is repointed by **`scripts/repoint_etf_listing.py`** (venues enumerated from the ISIN itself). Pinned by `tests/test_repoint_primary_listing.py`. **The lesson: the protection was incidental, therefore invisible, therefore removable without anyone noticing.**
- GuruFocus subscription covers USA + **continental** Europe + Asia (incl. Middle East) EXCEPT **India** (NSE/BOM — note GuruFocus + IBKR use `BOM`, not `BSE`, for the Bombay exchange; our DB stores `BOM`), **UK** (LSE), and **Ireland** (DUB) — GF returns "403 unsubscribed region" for those (confirmed by probing every exchange); Russia, Africa, LatAm, AU/NZ also out of scope — see `FEASIBLE_GF_EXCHANGES` in `backend/index_universe/acwi/exchange_map.py`. **US OTC Pink (`OTCPK`) IS covered** (USD) — GuruFocus prices US OTC tickers, so UK/foreign names with a US OTC line (e.g. QinetiQ → `OTCPK:QNTQF`) are fixable to a priceable listing instead of staying on their out-of-scope home exchange. - **Duplicate prevention**: two companies are the same security iff they share an **ISIN**. `ingest/dedupe.py::dedupe_by_isin` merges same-ISIN rows of the same company (name-root match, ignoring ADR/ADS) keeping the **Leonteq holding, else USA/EU** listing; it runs at the end of every `backfill_isin` so cross-universe dupes can't persist. The `/companies` DUPE badge is ISIN-based (NOT name-based — name-matching false-flags GOOG/GOOGL-style share classes that have *different* ISINs). The name key strips only trailing corporate-form suffixes (Inc/Ltd/Corp/SA/ADR/…) so "Celestica" ≡ "Celestica Inc" but "BYD Co" ≠ "BYD Electronic"; the no-ISIN condition keeps legitimate both-have-ISIN share classes from flagging. Surfaced as a header count + filter + per-row badge. **Prevention**: `ingest/dedupe.py::merge_name_dupes_keep_isin` auto-folds a no-ISIN stub into the same-name ISIN row — runs after `dedupe_by_isin` (in `backfill_isin`) and in the prune phase (`ingest/phases/prune.py`). SAFE by construction: acts only on a name bucket with **exactly one** ISIN-bearing company, and folds a stub only when `_foldable_names` holds (the stub's name is the keeper's name plus *only* trailing corporate suffixes — so `Celestica`→`Celestica Inc` and `HDFC Bank Ltd`==`HDFC Bank Ltd` fold, but `Siemens Ltd` (India) does **not** fold into `Siemens AG`, nor `Apple`→`Apple Hospitality`). ## Deployment

Frontend → Vercel, backend → Railway (long SSE streams OK, no timeout), DB → Supabase (all free tier). Push to `main` to deploy (both auto-deploy from GitHub). Railway runs `uvicorn main:app` with dashboard env vars.

### Weekly current-picks cron (Railway)

Railway Cron fires `POST /api/momentum/current-picks/cron` at **02:00 UTC Monday** with `-H "X-Cron-Secret: $CRON_SECRET" -d @/app/cron-current-picks.json` (config = a `BacktestRequest`). The endpoint forces `mode=current_portfolio` + `force_recompute=true` regardless of body, persists `triggered_by='auto'` + upserts `current_picks_day`. To change the strategy, edit the payload file; to pause, disable in Railway. *(Current-picks is otherwise on-demand from the UI buttons — not scheduled.)*

### In-process pipeline (`backend/scheduler.py`) — split into three operations (2026-06-08; month-end refresh added 2026-06-15)

The pipeline is split into **three independent operations** that the /schedule "Smart pipeline activity" card exposes as stacked sections (each with its own status + **Run now**). They **never run concurrently** — a module-level `_PIPELINE_LOCK` in `ingest/phases/pipeline.py` serializes them (the contended one shows "Waiting for another pipeline operation to finish…" then runs). Each is its own `ingest_run` row + `job_name`. Orchestrators in `ingest/phases/pipeline.py`:

- **`price_update`** (`_run_price_update_pipeline_sync`) — keep the enabled strategies' **held companies** (~the 24 currently held) priced + re-price open positions (MTD). Scope: held companies only (the union of every enabled strategy's latest-snapshot holdings — `_collect_held_company_ids`). Phases: prices (`_collect_held_companies` → `_run_prices_phase(companies_override=…)`) → **held ETF benchmarks** (`refresh_held_benchmarks` — re-fetches `benchmark_price` for the ETF-overlay holdings, negative company_id = `-benchmark_id`, which `_collect_held_company_ids` drops; without it a held ETF's price/`exit_date` went stale vs the held companies) → momentum **price-update only** (`_run_momentum_phase(include_rebalances=False)`). No template maintenance, no universe refresh, no rebalance. **Stale-price retry**: after the op (any trigger — daily tick, startup catch-up, manual Run-now), `scheduler.maybe_schedule_price_retry()` schedules a one-shot retry **+3h** out (`PRICE_RETRY_DELAY_HOURS`, job id `price_update_retry`) when ≥1 *active* held name's latest close is behind the **global** freshest close — GuruFocus publish lag (`held_prices_lagging` in `ingest/phases/prices.py`, anchored to the global latest like the delisting sweep, NOT the calendar day, so the normal "today's close isn't out yet" state and a full GuruFocus outage don't false-trigger; delisted/out-of-scope/illiquid held names are skipped). Bounded to `PRICE_RETRY_MAX_PER_DAY` (=3) retries/UTC-day; the next 05:00 tick takes over after that. The retry re-runs the whole op but the per-company freshness short-circuit means only still-stale names hit the API. **EUR basis**: the price-update re-pricer (`compute_and_save_price_update` in `routers/_schedule_snapshots.py`) converts each held position's latest close to EUR at the fx_rate-table rate for the exit date (entry uses the rebalance's stored EUR mark, itself the fx_rate at the entry date) before computing `forward_return_pct` + the weighted `period_return_pct` — so the held-basket return is in EUR (incl. the FX leg over the holding period), consistent with the EUR daily curve + the rest of the (€) UI. (Until 2026-06-30 it computed those off **local** prices, silently dropping FX — a USD/JPY holding's return diverged ~FX% from EUR.) The /schedule header MTD, when the open period started this calendar month, is set to this same per-snapshot `period_return_pct` (`_schedule_hydration._hydrate`), so the header, the Current-portfolio card (weighted `forward_return_pct`), and the engine all read the identical EUR held-basket return.
- **`rebalance`** (`_run_rebalance_pipeline_sync`) — rebalance the **due** strategies (re-select from a fresh universe). No-op (status ok) when nothing is due. Phases: plan (`build_plan`) → templates (refresh ONLY the due strategies' universes + derived parents) → dedupe (gated on a template rebuilding) → prices (`collect_universe_companies` — the due strategies' full universe) → momentum **rebalance only** (`_run_momentum_phase(include_price_updates=False)`).
- **`full_price_refresh`** (`_run_full_price_refresh_pipeline_sync`) — **month-end** full price/volume refresh of **EVERY** company (most-stale first), **bounded by the monthly GuruFocus quota** per region. Prices only (no templates/prune/momentum). `_run_prices_phase(budget_by_region=remaining_budget(supabase))`: `region_remaining` (per region `{usa,europe,asia}` = `MONTHLY_API_LIMIT - used`, from `ingest/api_usage.py`) is decremented by each fetch's real `PriceResult.api_calls`; a region at ≤0 **skips** its remaining companies (`budget_skipped` counter + "X skipped (monthly budget reached)" message) instead of erroring against an exhausted quota. The quota resets midnight EST on the 1st, so this spends what's left before it's lost.

`_run_momentum_phase` gates: `include_rebalances`/`include_price_updates` pick which branch runs per strategy (Branch A price_update / Branch B rebalance). All ops finalize via `_finalize_run`.

**Scheduling** — one daily `BackgroundScheduler` tick at **05:00 UTC** (~07:00 CEST; `id="daily_pipeline"`, fires `_fire_daily_sequence`) runs **price-update then rebalance in order**, in one daemon thread (so they're sequential, not racing). It's 05:00 (not 02:00) so the slower-publishing European EOD closes (XPAR/MIL/XAMS) are in GuruFocus by run time — at 02:00 UTC held EU names lagged a day. The month-end `full_price_refresh` (`id="month_end_price_refresh"`) runs on a **daily 12:00-UTC tick** but `_fire_month_end_refresh` gates it to the **last `MONTH_END_WINDOW_DAYS`+1 days of the month** (env, default 2 → the 28th–30th of a 30-day month) AND to "no successful full/`manual` run since the window opened". So it fires once near month end, and if that day's run is missed (deploy/restart) or errors, the **next day in the window retries** — replacing the old single `day="last"` tick that a deploy in its 1h grace could drop for a whole month (which once left hundreds of companies stale). It's NOT startup/every-deploy triggered — only end-of-month. 12:00 UTC = 07:00 EST is safely inside the EST usage month (resets midnight EST on the 1st). `MONTH_END_WINDOW_DAYS=0` → last day only. On startup, `_maybe_kickstart_smart` fires the daily sequence once if a strategy is due or held prices are stale (catch-up after downtime) — this covers HELD prices only, deliberately not a full reprice. A daily tick **`id="asset_price_refresh"`** (`CronTrigger(hour=6, minute=0)`, `_fire_asset_price_refresh` → `asset_pipeline/price_refresh.py`) is the **`asset_price` twin of the 05:00 GuruFocus price update** — the Yahoo/`asset_execution` universe never had one, so it aged **silently** (a stale series still prices, still charts; it is just old). Measured 2026-07-14: **197 of 223 held instruments were stale**, and a model portfolio whose window opened *after* its holdings' last close rendered **blank rows** (Meta Platforms, correctly mapped to `META` with 3,556 bars, showed nothing in `BUS_2.0_NEU_FX` — window 2026-07-09, last close 2026-07-02: no price *inside* the window, so no return over it exists). Three rules: **staleness is measured against the freshest close WE HOLD, never the calendar** (else every weekend flags the fleet, and a Yahoo outage orders a full refresh at the one moment refreshing achieves nothing — same anchor as the delisting sweep); it fetches **the GAP, not the history** (`store.extend_series`, ~1.5s/row — `store_series` re-downloads KO's 16,239 bars back to 1962 to add eight days, and ⚠ **derives `price_from`/`bars` FROM THE ROWS IT FETCHED**, so a windowed call would record "KO has 8 bars beginning 2026" and truncate its parquet: `extend_series` recomputes those stats **from the DB** and returns `None` rather than guess, falling back to the full path); and it **stands down while the ingest-queue WORKER is live** (`queue.is_worker_active()` — Yahoo answers an overloaded caller with an EMPTY result, not a 429, and that is how a resolution lands on a thin foreign listing). ⚠ **That guard must read the WORKER, not the BACKLOG**: the first version gated on `pending > 0` and never ran once — the queue holds **9,945 pending ISINs last touched a week earlier**, a stalled backlog, and `status()["working"]` is just `pending > 0`, so it calls an abandoned queue "working". `is_worker_active()` reads the real heartbeat (when a row was last *moved* out of pending). **It also fires ON STARTUP** (`_maybe_kickstart_asset_prices`, mirroring `_maybe_kickstart_smart`): a daily tick keeps prices current going *forward* but **cannot repair the past**, so a backend that was down over a weekend — or a fresh deploy — would serve blank /management-dashboard rows until 06:00 the next morning. It **detects before it fetches** (a few queries, one grouped COPY), so `uvicorn --reload`'s constant restarts are a near-free no-op rather than 220 Yahoo calls; the queue guard lives in the shared body, so the startup path cannot slip past it. ⚠ **It logs at WARNING when it finds work** — uvicorn leaves the ROOT logger at `WARNING`, so an `info` line is invisible in production (this is why the first boot test appeared to do nothing); the healthy no-op case stays at `info` so a clean restart is quiet. Verified end-to-end: META artificially aged to 2026-07-02 → boot → *"2 of 224 held instrument(s) stale … 1 moved"* → back to 2026-07-13 with `bars=3556, price_from=2012-05-18` intact. Manual twin: `scripts/refresh_asset_prices.py --held [--apply]`, which calls the **same** function (a cron that drifts from the script you debug with is a cron nobody trusts). Pinned by `tests/test_asset_price_refresh.py`. A daily tick `id="fx_sync"` (`CronTrigger(day_of_week="mon-fri", hour=16, minute=30)` — after the ~16:00 CET ECB publication; `_fire_fx_sync`) syncs EVERY fetchable currency's `fx_rate` (ECB + USD-pegs + TWD) so the /fx-rates page shows all currencies current — the daily pipeline only syncs the *held* strategies' currencies (a side effect of the momentum backtest stream), so unused ACWI currencies would otherwise go stale. Idempotent (`sync_fx_rates_to_db` fetches only the gap). The /fx-rates page surfaces per-currency freshness (date + a green/amber/red dot anchored to the freshest rate, 1-trading-day tolerance for the ECB-vs-pegged source skew). Manual Run-now → `POST /api/ingest/scheduled-refresh/trigger?job_name=price_update|rebalance|full_price_refresh` (admin Bearer via `apiFetch`); manual FX sync → `POST /api/fx/sync`.

**Dropped vs the old smart pipeline**: template-universe *maintenance* (auto-refreshing ACWI/LongEquity to the calendar month so /backtest + /acwi stay current with zero strategies). The rebalance op refreshes only the *due strategy's own* universe on demand — so universes no enabled strategy uses (ACWI, LongEquity) go stale until a manual full refresh. This intentionally fixed the bug where a snapshot-fed template stuck behind the month (LongEquity at 2026-05) re-priced its whole 401-company membership on **every** tick.

The legacy `_run_smart_pipeline_sync` (job `smart_daily`) + `_run_pipeline_sync` (jobs `manual`/`bootstrap_template_refresh`, full refresh-all) remain valid `job_name`s (dispatch in `routers/ingest_runs.py`), just no longer fired by the scheduler. `manual` = the full refresh-all pipeline (all five phases over every company).

**Trade-offs / gotchas**:
- ✅ Code-managed (deploys with `git push`; cron expression in `scheduler.py`).
- ⚠️ Single-instance assumption — the `_PIPELINE_LOCK` is in-process, so it only serializes within one replica. Set `DISABLE_SCHEDULER=1` on all but one if you scale out (also the pause switch).
- ⚠️ A restart landing exactly at 05:00 UTC drops that tick; the startup kickstart catches up.
- `POST /api/ingest/scheduled-refresh/cron` (X-Cron-Secret) still exists for reverting to Railway Cron — pass `job_name=price_update`/`rebalance`.
